# Personal portfolio chatbot

The floating **Ask about me** button opens a chat grounded in Sreeved's portfolio. The browser sends messages to `/api/chat`; a Vercel Node.js function checks shared request limits, retrieves relevant text from Upstash Vector, and asks DeepSeek through OpenRouter to answer from those excerpts. Retrieved sources appear below each answer. No API credentials are sent to the browser.

## Activate it

1. Copy `.env.example` to `.env.local`. This file is ignored by Git. Put your OpenRouter API key in `OPENROUTER_API_KEY`. The default model is `deepseek/deepseek-v3.2`; change `OPENROUTER_MODEL` to another available DeepSeek model if desired.
2. Configure a **dense Upstash Vector index**. Set `UPSTASH_VECTOR_REST_URL` and its **read/write** `UPSTASH_VECTOR_REST_TOKEN` in `.env.local`. The app reads the index configuration automatically. If a hosted embedding model is enabled (for example, `BAAI/bge-m3`), Upstash embeds the text. If no hosted model is enabled, OpenRouter generates vectors using `OPENROUTER_EMBEDDING_MODEL`, which defaults to `openai/text-embedding-3-small`, with the index's dimension count. This default works with a 1,536-dimensional index. The same OpenRouter API key is used; embedding calls consume credits separately from DeepSeek replies.
3. Create an Upstash Redis database and copy `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` into `.env.local`. Redis enforces limits across Vercel instances. Defaults are ten requests per visitor per 60-second window and 200 requests globally per 24-hour window, starting with the first accepted request. Failures after reservation also count. The API does not generate replies if this check fails.
4. Review your portfolio facts and run `npm run rag:check` to see the documents to be indexed. Run `npm run rag:ingest` to embed and store them. Wait for Upstash indexing to finish before testing. This is an owner-run command, not a public upload endpoint.
5. Import this repository into Vercel with the **Vite** preset. The included `vercel.json` builds the frontend and deploys `api/chat.ts`. Add the server variables from `.env.local` to Vercel's Environment Variables. For Vercel's vector token, use the index's **read-only** token. Leave `VITE_CHAT_API_URL` empty to use the same-origin function. Deploy the same source revision that you indexed.
6. Run `npm run dev` locally or visit the Vercel deployment. Try “What has Sreeved built?”, then “What tools did he use?”, and a question absent from your notes. Verify the retrieved sources and the answer quality. Local development uses the same handler with a local API middleware. `npm run preview` serves only static output; it does not run the API.

Credentials and Vercel account access are required to upload vectors and verify real model replies. A successful local build or mocked test does not mean those services have been provisioned.

### HTTP 422 during ingestion

An index created with dimensions but no hosted embedding model accepts vectors, not `/upsert-data` text uploads. The updated code detects this and uses OpenRouter's embeddings API, followed by Upstash's `/upsert` endpoint. Retrieval uses the same embedding model and Upstash's `/query` endpoint. Your existing index does not need to be deleted or recreated. DeepSeek remains the reply model.

For external embeddings, leave `OPENROUTER_EMBEDDING_MODEL` unset to use the default, or set it identically in `.env.local` and Vercel. If you choose a different model, it must support the dimensions of your index. Re-ingest and redeploy after changing it. An embedding-model fingerprint is added to the knowledge namespace so vectors generated by different models cannot be mixed. `npm run rag:check` is offline and shows only the base namespace; ingestion reports the final namespace after reading the index. Error messages distinguish authentication, credits, index configuration, and embedding response problems without logging provider bodies or secrets.

## Add more information about yourself

`server/knowledge.ts` explicitly includes your bio, contact links, skills, experience, project details, and the saved Medium article titles/excerpts. It excludes legacy placeholder writing entries and does not crawl arbitrary files, email, or social profiles. The Medium snapshot is not the full text of your articles and is not automatically refreshed for RAG.

Add additional facts to `knowledge/personal.json` using this shape:

```json
[
  {
    "title": "Education",
    "text": "Replace this with your actual qualification, institution, and dates."
  },
  {
    "title": "A project you want to explain",
    "text": "Replace this with the actual problem, your contribution, technologies, and outcome.",
    "url": "#work"
  }
]
```

The current file is intentionally empty until you add real facts. This is public chatbot knowledge: include only information you want visitors to receive. Keep API keys, passwords, confidential work, and private personal information out of all knowledge files. The repository's existing metrics and dates are treated as your supplied claims; review them before indexing. The bot cannot know facts you have not supplied.

After changing any knowledge source, run `npm run rag:ingest` again and redeploy. The namespace contains a hash of the complete knowledge set. Changed or removed facts therefore cannot leave stale chunks in the active namespace. Existing deployments keep using their previous namespace until redeployed. Old namespaces are retained for rollback; remove unused ones manually in Upstash after those deployments are retired. Re-running ingestion on unchanged content uses the same IDs and namespace. If an upload is interrupted, rerun it to complete every batch before deploying.

`RAG_MIN_SCORE=0.5` is an initial cutoff for dense normalized similarity scores, not a guarantee of answer correctness. Tune it using real example questions for your chosen embedding model. Low-scoring results return an “I don't have that information” response without calling the model. An empty index returns an unavailable/setup state. Higher-scoring excerpts are still subject to the model's explicit unknown-answer instructions.

## Keep the existing GitHub Pages URL

GitHub Pages cannot run the server function. You can host the backend on Vercel while keeping the public portfolio on Pages:

1. Deploy this project to Vercel as above.
2. Set `CHAT_ALLOWED_ORIGINS=https://sreevedvp.github.io` in Vercel and redeploy. This is an origin, without `/portfolio/`. Additional origins can be comma-separated; wildcards are not supported.
3. In GitHub repository **Settings → Secrets and variables → Actions → Variables**, set the repository variable `VITE_CHAT_API_URL` to `https://YOUR-PROJECT.vercel.app/api/chat`. The existing Pages workflow now reads it at build time. Re-run the workflow or push your changes.

`VITE_CHAT_API_URL` is a public URL, not a secret. Never put an API key in it or in any `VITE_` variable. Use the production Vercel URL accessible to your visitors, not a protected preview URL. CORS restricts browsers; it is not authentication. Shared request limits also cover direct API calls. Configure an OpenRouter key credit limit to cap actual spend; request caps are not a currency budget.

## Secrets and data handling

- `.env.local`, `.env`, environment variants, `.vercel/`, and key files are ignored by Git; only the blank `.env.example` is tracked. Do not force-add secrets. If a real secret was previously committed, ignoring it does not remove Git history; rotate it.
- The browser imports only `src/services/chat.ts`. OpenRouter, Vector, and Redis credentials are used only in server code or the local ingestion command. No secrets are included in model prompts, API error bodies, or application logs.
- Only approved knowledge chunks are stored in the vector database. With hosted embeddings, Upstash receives knowledge and retrieval text. With external embeddings, OpenRouter and its embedding provider receive the knowledge text during ingestion and the current question/recent context during retrieval; Upstash stores the resulting vectors alongside the knowledge text and metadata. Conversation messages stay in browser memory for the current page session and are sent to OpenRouter/model providers for answering. The app does not save transcripts in its database. Provider retention policies still apply.
- Redis stores expiring counters under an HMAC of the visitor IP, not raw IP addresses or message text. Vercel's trusted forwarding header is used in production; all local requests share a development counter.
- Input length, conversation roles, timeouts, fixed generation limits, safe source links, and generic provider errors are enforced. Model output is rendered as text, not executable HTML. The prompt asks for grounded answers, but model-level prompt injection and hallucination cannot be ruled out; never ingest confidential information.

## Checks

```sh
npm run lint
npm test
npm run rag:check
npm run build
```

Tests mock external services and cover retrieval, follow-ups, missing information, input validation, request limits, provider outages, source links, and credential separation. They do not consume paid API calls. Real answer quality and the Vercel deployment must be checked after adding credentials.
